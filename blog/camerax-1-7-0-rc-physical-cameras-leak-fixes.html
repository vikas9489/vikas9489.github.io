CameraX 1.7.0-rc01 and rc02: Physical Camera Binding, Camera2Interop Abstract Classes and the Leak and Crash Fixes

CameraX 1.7.0 skipped beta entirely: after the alphas it went straight to 1.7.0-rc01 (Oct 21, 2026) and 1.7.0-rc02 (Nov 4, 2026). Release candidates are where API shape freezes, so this is the moment to check your Camera2 interop code and your lifecycle handling. Everything below comes from the official AndroidX Camera release notes, retrieved today.

rc01
Oct 21, 2026: API changes and most fixes
rc02
Nov 4, 2026: two bug fixes, no API changes
Physical
cameras can now be bound directly

1. Physical cameras are first-class

rc01 adds support for physical cameras. CameraInfo.getPhysicalCameraInfos() now returns physical camera info, apps can bind UseCases to physical cameras, and querying CameraInfo with a physical CameraSelector returns the physical CameraInfo instead of the logical one. That last point is a behavior change: if you previously passed a physical selector and relied on getting the logical camera back, re-test.

val provider = ProcessCameraProvider.awaitInstance(context)
val logical = provider.availableCameraInfos.first()

// One entry per physical sensor behind the logical camera (wide, ultrawide, tele...)
val physical = logical.physicalCameraInfos
physical.forEach { info ->
    Log.d("Cam", "physical camera: $info, zoom=${info.intrinsicZoomRatio}")
}

The snippet only shows the discovery call named in the notes; the notes do not spell out the selector construction for binding, so check the CameraX reference for your version before wiring it into a lens switcher. Also in rc01, CameraInfo.getIntrinsicZoomRatio() now rounds its result to two decimal places, which is handy when you display zoom labels.

2. Camera2Interop: interfaces become abstract classes

rc01 converts four types from interfaces into abstract classes: UseCaseCamera2Interop, ImageCaptureCamera2Interop, SessionConfigCamera2Interop and CameraControlCamera2Interop. It also fixes the Camera2Interop V2 ambiguity issue. If your code implements one of these as an interface, it will no longer compile as written; this is the main source-breaking item in the release.

Why it matters: abstract classes let the library add methods without breaking implementers. It is a signal that these interop surfaces are being stabilized for 1.7.0 final, so migrating now is cheaper than migrating after release.

3. Low Light Boost and Torch: last setting wins

Previously, enabling one of these while the other was active could be rejected. In rc01 they follow a "last setting wins" policy: enabling one automatically disables the other instead of rejecting the request. The notes also say flash can fire during image capture while Low Light Boost is active. If your UI shows both toggles, observe camera state instead of assuming both stay on.

4. Crash and leak fixes you should care about

  • OpenGL thread SIGSEGV: a native crash occurred when a SurfaceProcessor released an input SurfaceTexture whose SurfaceRequest had been garbage-collected before completion. Fixed in rc01.
  • CameraEffect shutdown: a Surface leak and native OpenGL crash during garbage collection happened when a CameraEffect's executor or HandlerThread shut down before the effect's SurfaceOutput was closed. Fixed in rc01.
  • ImageAnalysis: a Surface/ImageReader resource leak when output rotation changed dynamically or the use case was unbound. Fixed in rc01.
  • PRIVATE format check: the HardwareBuffer.isSupported check for PRIVATE format in ImageAnalysis was relaxed to avoid false negatives on some devices. Relevant if you adopted the GPU-native analysis path from the alphas.
  • VideoCapture: a native thread leak on unbind, which left one media framework thread behind per bind. Fixed in rc02.
  • API 30 overlay apps: an UnsupportedOperationException when apps holding SYSTEM_ALERT_WINDOW repeatedly bind camera use cases. Fixed in rc02.

The VideoCapture and ImageAnalysis leaks share a pattern: they accumulate with repeated bind/unbind cycles. Apps that rebind on every screen visit or rotation were the most exposed.

5. Smaller items

  • The androidx.lifecycle:lifecycle-runtime dependency moves to 2.10.0, required for bundled lifecycle runtime lint checks with AGP 9.5.0-alpha04 or later.
  • A compilation crash on newer JDK versions, when resolving transitively imported JSpecify annotations on CameraX internal fields, is fixed.
  • OutputOptions.Builder.setLocation Javadoc now states that only latitude and longitude are stored in video metadata.

Upgrade checklist

  1. Bump all androidx.camera:camera-* artifacts to 1.7.0-rc02 together.
  2. Search for implementations of the four Camera2Interop types and convert them to subclasses.
  3. Re-test any code that uses a physical CameraSelector with CameraInfo queries.
  4. Remove workarounds you added for the VideoCapture thread leak or the ImageAnalysis rotation leak.
  5. Check torch and Low Light Boost toggles against the last-setting-wins behavior.

If you ship camera features, rc02 is a sensible target: the only differences from rc01 are two bug fixes, so the API surface you migrate to now is the one you should expect at 1.7.0.

Source: AndroidX Camera release notes (1.7.0-rc01, 1.7.0-rc02) and the AndroidX release listing, developer.android.com, retrieved Nov 14, 2026.
