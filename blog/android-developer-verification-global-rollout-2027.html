Android Developer Verification Goes Global in January 2027: Developer ID Status API, Console API and What to Do in CI

Android developer verification is leaving its four-country pilot. Google's Nov 19, 2026 post says the user protections went live on September 30 for participating stores in Brazil, Indonesia, Singapore and Thailand, and that the global rollout begins in January 2027, in partnership with seven distributors: Google Play, Galaxy Store, Honor, Oppo, Xiaomi, Transsion and Vivo. Protections then expand gradually to all countries, covering all installation sources on certified Android devices, over several months.

1. What is new since the pilot

  • Adoption: Google says millions of apps have been registered globally since verification opened to everyone in March, representing over 99% of all Android app installs globally.
  • Limited distribution accounts: launched in August for students and hobbyists who want to share apps without registration fees or verifying a government ID. The sharing limit is now 50 authorized devices, up from 20.
  • Advanced flow: experienced users can install unregistered apps by accepting the risk, with guardrails kept in place against social engineering scams for everyday users.
  • Automation APIs: the Android Developer ID Status API and the Android Developer Console API, aimed at teams managing many apps and at CI pipelines.

2. Which path applies to you

  • Google Play developers: check package registration status in Play Console and register anything unregistered, including apps you distribute outside Play.
  • Distributing only outside Play: create an Android Developer Console account to verify identity and register apps.
  • Open-source registries and distributors: Google published new dedicated guides for both.

If you ship a sideload APK, a beta channel or an enterprise build next to the Play version, the Play registration does not cover your mental checklist for those: register them too, or users on certified devices may hit the install block once their region goes live.

3. Gate your release pipeline on registration status

The Developer ID Status API is a server-to-server check at https://androiddeveloperidstatus.googleapis.com. It authenticates with an API key sent in the X-Goog-Api-Key header. CheckPackageRegistrationStatus returns one of three states: REGISTERED, NOT_REGISTERED, or, when you pass a certificate fingerprint, REGISTERED_WITH_ANOTHER_CERTIFICATE_FINGERPRINT. The default quota is 1,000 requests per project per day, so cache results rather than checking every build of every module.

The check accepts the SHA-256 fingerprint of the signing certificate as the certificateFingerprint query parameter. A small Kotlin helper that fails a release job on anything but a clean match:

import java.net.URI
import java.net.URLEncoder
import java.net.http.HttpClient
import java.net.http.HttpRequest
import java.net.http.HttpResponse

enum class RegistrationState {
    REGISTERED, NOT_REGISTERED, REGISTERED_WITH_ANOTHER_CERTIFICATE_FINGERPRINT
}

fun checkRegistration(apiKey: String, packageName: String, sha256: String): RegistrationState {
    val fp = URLEncoder.encode(sha256, Charsets.UTF_8)
    val url = "https://androiddeveloperidstatus.googleapis.com/v1/packages/" +
        "$packageName/packageRegistrationStatus:check?certificateFingerprint=$fp"
    val request = HttpRequest.newBuilder(URI.create(url))
        .header("Accept", "application/json")
        .header("X-Goog-Api-Key", apiKey)
        .GET()
        .build()
    val response = HttpClient.newHttpClient()
        .send(request, HttpResponse.BodyHandlers.ofString())
    check(response.statusCode() == 200) { "HTTP ${response.statusCode()}: ${response.body()}" }
    val state = Regex("\"state\"\\s*:\\s*\"(\\w+)\"").find(response.body())!!.groupValues[1]
    return RegistrationState.valueOf(state)
}

Treat the error status field, not the English message, as the stable contract: Google says the message text can change. 429 (RESOURCE_EXHAUSTED), 500 and 503 are retryable; 400, 401 and 403 are not, and a 403 most often means the API is not enabled in your Cloud project.

4. Registering from CI: the Developer Console API

The Developer Console API registers package names and keys programmatically. Its authentication is the notable constraint: it requires OAuth 2.0 because developer account data is tied to a user's Google Account, and the documentation states that service accounts, Workload Identity Federation and API keys cannot be used. The recommended CI setup is a one-time browser consent with access_type=offline, then storing the refresh token in a secret manager or CI secrets so pipelines can mint short-lived access tokens without a login or 2FA prompt. The scope is https://www.googleapis.com/auth/androiddeveloperconsole.

The flow the guide describes is: CreateAndroidPackage, then GetAndroidPackageRegistrationPolicy to learn the key eligibility rules, then CreateAndroidPackageKey. If the returned key state is DRAFT, you must prove ownership by putting the API-issued token in an adi-registration.properties file in the app's assets folder and uploading an APK signed with that key (VerifyAndroidPackageKeyOwnership). If it is IN_REVIEW, ownership checks were skipped because the package is new or the key was already verified for another package in the same account. A key marked as requiring justification needs a business rationale submitted through JustifyAndroidPackageKeyRegistration, and the guide says approval can take up to 24 hours.

5. Existing package names and key eligibility

For a package name already seen on Android, eligibility is decided by install share: a key holding over 50% of known installs gets priority; if none does, every key with 50 or more installs is eligible; below that threshold it is first come, first served. Other developers must justify their claim. The practical lesson for anyone who inherited an app, reuses a package name from a fork, or rotated keys: check the fingerprint pairing before release day, not on it.

Takeaway: verification is now a release-pipeline concern. Register every package name you ship through any channel, add a fingerprint-aware status check as a pre-release gate, and keep a CI-friendly OAuth refresh token for the Console API rather than relying on someone clicking through a web form before each launch.
